# Tarati AI Engine

How the Tarati engine works after the 2026 rebuild, and which parameters you can
tune. Two implementations are kept in lockstep:

- Python (offline): `strategy/engine/ai.py` on the bitboard core in
  `strategy/engine/bitboard.py`
- JavaScript (in-app): `src/AI.js`

A golden fixture (`src/__tests__/parity-fixture.json`, generated by
`strategy/export_parity_fixture.py`) pins the two together: both must agree on
legal moves, evaluation, and the chosen move at fixed depth across ~380
positions. `src/__tests__/aiParity.test.js` enforces it.

## 1) Search

Negamax with alpha-beta pruning and iterative deepening. The score is relative
to the side to move; the public `evaluate_board` keeps the historical
"positive favours WHITE" convention.

- **Iterative deepening.** The root is searched to depth 1, then 2, and so on,
  keeping the best move from the previous pass as the first move to try. With
  `max_ms`/`max_nodes` set, the last completed depth is returned (anytime
  behaviour); with neither set the search runs to the requested depth.
- **Full-window root.** Every root move is searched with `(-inf, +inf)`. The
  old engine narrowed alpha/beta across sibling root moves, which turned every
  root score after the first into a bound rather than a value and corrupted both
  the move choice and the sampling below.

## 2) Terminal scoring

A player who cannot move has **lost**, however much material they hold. At a
game-over node the side to move is the loser, scored `-(WINNING_SCORE - ply)` so
that faster wins are preferred and longer losses resisted.

The previous engine used `material < 0 ? +WIN : -WIN` — material sign as a proxy
for the winner. That is wrong whenever a player is ahead but jammed, which in a
game with forward-only movement is the single most important losing pattern.
`test_search.py` locks this down with a position where White leads four pieces
to three yet is stalemated, and must score as a loss.

## 3) Transposition table

`TranspositionTable` holds two maps:

- `values`, keyed by **(position, depth)**. A value is reused only at the exact
  depth it was searched to. Chess engines reuse any entry of greater-or-equal
  depth, but in fixed-depth minimax the depth-8 value of a position is a
  different quantity from its depth-5 value, so a depth-8 bound licenses no
  conclusion about a depth-5 window. Reusing it anyway lets a bound masquerade
  as an exact value and corrupts scores upward. Entries carry an
  EXACT/LOWER/UPPER flag, and mate scores are re-based by ply on store and load.
- `moves`, keyed by **position** alone: the best move found at any depth is
  worth trying first, which is what makes iterative deepening pay for itself.

`test_search.py` checks that enabling the table never changes the chosen move or
any root score.

## 4) Evaluation

Static evaluation is in **centipieces** (100 = one piece), summed over set bits
of the board with per-square value tables:

- material, and a bonus for roks (upgraded pieces)
- centre terms: the A1 hub and the B-ring
- advancement for cobs (roks excluded — they move freely, so how far up the
  board they sit says little)
- home-base integrity, and a penalty for a cob dead on the opponent's outer
  home points
- mobility, the difference in legal-move counts

Every term is built on `RANK` or on vertex sets that map onto their opposite
under the board's 180° rotation, so `eval(P) == -eval(rotate_and_swap(P))` holds
exactly. This colour symmetry is a test, not an aspiration: it is what makes any
large colour skew at equal strength diagnosable as a bug. Weights live in
`bitboard.EVAL_WEIGHTS` and are calibrated, not guessed.

Note the engine saturates near depth 10 — beyond it, more strength needs a
better evaluation rather than deeper search. And absolute values carry a
horizon offset (see §9); use per-move *loss* to judge moves, never the absolute
score.

## 5) Move ordering

A static heuristic that never applies the move: the transposition move first,
then captures (counted exactly via the pre-adjacency rule), promotions, and
forward progress. The old engine applied every candidate move just to sort the
list, which cost about a quarter of search time.

## 6) Temperature (move diversity)

`temperature` is a softmax width in **centipieces**. Root moves within `top_k`
of the best are sampled with weight `exp((score - best) / temperature)`, so at
25 a move half a piece worse is played about 14% as often as the best.

The old `stochastic_top_k` softmaxed raw scores whose unit was ~100 per piece,
making `exp(-100)` a uniform tie-breaker that did nothing. Set `temperature = 0`
for deterministic best-move play.

## 7) Difficulty tiers

App difficulties are **measured**, not assigned by depth. `05_calibrate_ladder.py`
plays a colour-balanced round robin among candidate configurations and fits Elo
with confidence intervals; `src/config/aiConfig.js` maps Easy/Medium/Hard/
Champion onto the resulting tiers (0 / 454 / 742 / 1094 Elo). The previous
ladder mapped difficulty to raw depth and was wrong: depths 12–20 were a single
player, and depth 9 lost to depth 6.

## 8) Key tunables

| Parameter | Effect |
|-----------|--------|
| `depth` | maximum search depth in plies |
| `max_ms` | wall-clock budget; returns the last completed depth |
| `max_nodes` | node budget; same anytime behaviour |
| `temperature` | softmax width in centipieces; 0 = always best |
| `stochastic_top_k` | how many root moves are sampling candidates |
| `blunder_rate` | probability of deliberately taking the 2nd/3rd best move |
| `use_tt` | enable the transposition table |

`root_probe_nodes` is accepted for backward compatibility and ignored; the
round-robin root probing it configured is gone.

## 9) What the engine is missing, measured

`10_engine_lab.py` benchmarks candidate improvements (implemented as flags in
`engine/search2.py`) against the shipped search. It gates on parity first: the
`base` variant must reproduce `ai.py` move-for-move and score-for-score, which
it does over 120 positions at depth 6. Nothing below is shipped yet — the
production engine is still pinned to `src/AI.js` by the golden fixture.

**There is no quiescence search, and it is the single biggest defect.** The root
score from the symmetric start oscillates by parity at every depth:

| depth | 6 | 7 | 8 | 9 | 10 | 11 | 12 | 13 | 14 |
|---|---|---|---|---|---|---|---|---|---|
| shipped | −28 | +30 | −28 | +33 | −29 | **+253** | **−235** | **+228** | **−221** |
| with quiescence | 0 | −18 | +1 | 0 | 0 | −22 | +1 | −7 | +19 |

The ±230 swing at depth 11+ was previously recorded as a *tempo effect* of the
game. It is not. It is the search stopping mid-exchange, and quiescence over
strikes and promotions removes it. The opening is balanced.

**The evaluation weights have three sign errors.** Fitting a depth-12 search's
verdict against position features over 92,769 labelled positions
(`09_mine_patterns.py`) prices the A1 hub at −74 cp against a shipped +18, the
B-ring at −37 against +10, and home occupancy at −8 against +8. Mobility is
priced at +31 against a shipped +3. A high-degree vertex is a vertex where more
enemies can arrive beside you, which the static table rewards instead of
charging for.

### Gauntlet results

Colour-balanced games from distinct ply-4 openings, **equal node budget** on
both sides (equal depth would hide the cost of an idea).

| variant | flags | vs `base` @25k, 120 games | @100k, 80 games |
|---|---|---|---|
| `order` | killers + history + PVS | +52 [−10, +115] | — |
| `quiet` | quiescence | +101 [+37, +166] | — |
| `mined` | refitted weights | +76 [+13, +140] | — |
| `threat` | one-ply strike-threat eval term | +107 [+43, +172] | — |
| `quiet+ord` | quiescence + ordering | +120 [+55, +186] | — |
| `mined+q` | weights + quiescence + ordering | +241 [+164, +318] | +191 [+104, +278] |
| `full` | `mined+q` + threat term | +168 [+99, +238] | +127 [+46, +208] |
| `full+ttge` | `full` + depth≥ TT reuse | +161 [+93, +230] | — |

**Every variant beats the shipped engine, and the package is worth roughly +170
to +240 Elo.** That much is solid: both leaders' intervals clear zero by a wide
margin at both budgets, and the gain survives a four-fold budget increase.

**Which of the two leaders is better is not resolved, and the table above will
mislead you about it.** Played directly against each other over 120 games,
`full` scores +47 [−16, +109] on `mined+q` — the opposite order to their scores
against `base`, with an interval straddling zero. 120-game samples separate
either leader from `base` comfortably and cannot separate them from each other.
Do not read the +241 as "`mined+q` is the best variant"; read it as "`mined+q`
is one of two variants that are far better than what ships."

Head-to-head against `mined+q`, for reference:

| opponent | result |
|---|---|
| `full` | +47 [−16, +109] — not separated |
| `quiet+ord` | −53 [−115, +10] — not separated |
| `mined` | −183 [−254, −113] — clearly worse |

That last row is the informative one: refitted weights *alone* lose heavily to
the same weights with quiescence and ordering, so the search work is carrying
most of the gain, not the evaluation. Relaxing the exact-depth TT rule buys
nothing.

Ordering also makes the search 2.5x cheaper: depth 10 costs 96k nodes shipped,
37.7k with killers/history/PVS, 52k with quiescence on top.

**Null-move pruning is deliberately absent.** Its premise — that passing cannot
help you — is not obviously true in a game with irreversible forward moves.

### To ship this

Either leader would move Champion from a measured 1,094 Elo to roughly
1,220–1,340; the interval is wide because the two leaders are not separated from
each other. Before shipping, run `10_engine_lab.py --baseline mined+q` at 400+
games to settle it, or simply take `mined+q`, which is the cheaper evaluation
and has no term that a longer run could show to be dead weight.

It is not a drop-in either way: `src/AI.js` must gain the same quiescence,
ordering and weights, `export_parity_fixture.py` must regenerate
`parity-fixture.json`, and `05_calibrate_ladder.py` must re-run so the tiers stay
measured rather than assumed. `06_build_book.py` should rebuild too, since the
current book's absolute values carry the horizon offset above.

### The full re-label, and one measurement trap

The whole label set was re-scored with `mined+q` at depth 12 into
`data/labels_q.sqlite` (7h44m, 134,354 positions; `08_label_positions.py` gained
`--oracle` and `--out`, and the sampling seed is fixed so both label sets cover
the identical positions). Joined on those positions:

| | |
|---|---:|
| best move identical to the old oracle | 79.2% |
| strike/quiet class identical | 96.3% |
| old-"sharp" still sharp | 76.3% |
| old-decisive still decisive | 100% |

The guide's headline numbers barely move (quiet share of sharp positions
27.5% → 26.2%). What does move is the **endgame**: blunder rates rise at every
level once exchanges are played out before judging, because the old engine
stopped mid-exchange and silently forgave endgame errors. Expert endgame blunder
rate 3.6% → 3.7%, Intermediate 13.3% → 16.3%, Beginner 17.4% → 20.3%.

**The trap, recorded because it cost a wrong conclusion.** `search_root` uses a
null-window (PVS) root unless `temperature` is non-zero. That is fine for
choosing a move and fatal for reading one: with a null window every root score
after the first is a *bound*, so `best - runner_up` is meaningless. Measuring
gaps that way produced "94% of the guide's sharp positions are not sharp"; the
same positions, same engine, same depth, with a full-window root give 62.5%
still sharp. `ai.py` documents the identical hazard for the identical reason.
Any code reading a gap must pass a non-zero `temperature` — see `EXACT_ROOT` in
`13_depth_study.py`.

### Depth is not the lever

`13_depth_study.py` settles how deep the oracle needs to be. Against the depth-16
verdict on sharp positions:

| depth | agrees on the move | nodes/position |
|---|---:|---:|
| 8 | 90.6% | 12,652 |
| 10 | 93.8% | 42,326 |
| 12 | 93.8% | 128,782 |
| 14 | 94.4% | 366,755 |
| 16 | 100% | 962,691 |

Depth 12 → 16 costs 7.5x the nodes for six points of move agreement, and the
strike-versus-quiet classification the guide depends on differs from depth 16 by
0–1.9% at *every* depth from 8 up. A median corpus game is 29 plies, so depth 12
is already most of a game. Depth 12 is the right operating point.

`--stage drift` also checks whether stronger play visits different positions. The
door distribution shifts by at most 4.5 points, so those frequency tables
transfer. Stuck cobs are rarer in strong play (zero stuck cobs 58.0% → 72.8% of
the time), which supports the cramp chapter's advice rather than undermining it.
